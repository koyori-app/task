## 概要

Drive は Misskey のドライブに倣った、テナント単位のファイル管理スペースである。アップロードしたファイルをフォルダで整理し、タスクへの添付や共有 URL の発行に利用できる。ストレージは S3 互換（AWS S3 / MinIO）とローカルディスクの 2 種類で、環境変数で切り替える。このページには全体に効くアクセスの規則・設定・決定の記録を書き、機能ごとの規則は次のページに書く。

| ページ | 内容 |
|---|---|
| [ファイル](/features/drive/files) | multipart のアップロード、一覧、メタデータ、名前・配置・本文の更新、削除、配信、タスク添付、Markdown 本文の `KEY-N` の自動結び付け |
| [フォルダと共有](/features/drive/folders-and-sharing) | 階層フォルダ、`project_id` の継承・移動先の認可・プロジェクトルートの保護、利用者指定共有、公開リンク共有 |
| [クォータ](/features/drive/quota) | 使用量の取得、テナントの個別クォータの設定、アップロード・本文の更新時の検証 |
| [ドキュメント](/features/drive/documents) | プロジェクトのルートフォルダ直下の `.md` を読み書きする画面 |

## 振る舞い

### ファイルの URL

全ファイルの URL は `/v1/drive/files/{id}/content` に統一する。テナント一般ファイルもプロジェクトファイルも同じエンドポイントで、セッション・PAT・共有トークンのいずれかが要る。

S3 バックエンドでも S3 の直 URL はクライアントに渡さず、バックエンドが S3 からストリームで取得して応答する。DB には `storage_key` のみを保持し、API の応答を作るときに URL を組み立てる。

### ストレージバックエンド

バックエンドは `StorageBackend` trait（`upload` / `delete` / `get_stream`）で抽象化する。同じバックエンドに利用者のアバター画像も置く。キーは `avatar-{uuid}.{ext}` で、`drive_files` の行は作らず、規則の定義元は[アカウント設定](/features/account-settings)のアバターのアップロードである。

- `upload` はストリームを受け取る。`content_length` の `None` は長さ未知で、`Some` なら書いた長さと食い違うと `SizeMismatch` になる
- `get_stream` はプロキシ配信用のストリーミングダウンロードで、object が無いときはローカル・S3 とも `StorageError::NotFound` を返す
- ローカルの実装はチャンクを `BufWriter` へ順に書き込む
- S3 の実装は長さが未知（`None`）か 5 MiB 以上なら multipart upload を使い、5 MiB ごとに part を送る。5 MiB を超えて貯めず、途中で失敗したら abort する
- 単一 PUT（全量バッファ）は 5 MiB 未満と分かっている本文だけに使う。アップロード API は長さ未知、本文更新 API は既知の長さを渡す

S3 バックエンドはクレート `object_store`（`AmazonS3Builder`）を使い、S3 互換エンドポイント（MinIO / Cloudflare R2 / Backblaze B2 / Wasabi）に対応する。バケットは非公開でよい。

`S3_FORCE_PATH_STYLE` は URL の形式を選ぶ。AWS S3 は仮想ホスト形式（`bucket.s3.amazonaws.com`）が標準で、MinIO などのセルフホスト互換では `http://endpoint/bucket/key` の形式（パス形式）が要る。`true` に設定すると `AmazonS3Builder` の仮想ホスト形式を無効にする。

ローカルバックエンドは開発環境・セルフホスト向けで、`LOCAL_UPLOAD_DIR` で保存先ディレクトリを指定する。

### 設定

`apps/backend/.env` で設定する環境変数は次のとおりである。

| 変数 | 既定 | 内容 |
|---|---|---|
| `STORAGE_BACKEND` | `local` | `local` または `s3`。それ以外は起動時にエラー |
| `UPLOAD_MAX_SIZE_MB` | `100` | 1 ファイルあたりの上限（MB）。ファイル本体の上限で、multipart の境界とヘッダーは含めない |
| `DRIVE_SYSTEM_MAX_QUOTA_MB` | `51200`（50 GB） | テナントが設定できる容量の上限（MB）。`0` は上限なし |
| `DRIVE_DEFAULT_QUOTA_MB` | `10240`（10 GB） | テナントの既定の容量（MB）。`0` は無制限 |
| `S3_ENDPOINT` | | S3 用。例は `https://s3.amazonaws.com`、MinIO は `http://localhost:9000` |
| `S3_BUCKET` | | S3 用。例は `my-task-drive` |
| `S3_REGION` | | S3 用。例は `ap-northeast-1` |
| `S3_ACCESS_KEY_ID` | | S3 用。例は `AKIAIOSFODNN7EXAMPLE` |
| `S3_SECRET_ACCESS_KEY` | | S3 用。例は `wJalrXUtnFEMI...` |
| `S3_FORCE_PATH_STYLE` | `false` | S3 用。MinIO などでは `true` に設定する |
| `LOCAL_UPLOAD_DIR` | `./uploads` | ローカル用。例は `/var/task/uploads` |

### 脅威と対策

脅威ごとの対策は次のとおりである。

| 脅威 | 対策 |
|---|---|
| 他テナントのファイルへのアクセス | ファイル自身の `tenant_id` に対する所属を確認する。明示的な共有による本文アクセスは[認可](#認可)の節の例外に従う |
| プロジェクト外の利用者によるファイルアクセス | `drive_files.project_id` に対する公開規則とフォルダ共有を確認し、どちらでも許可されなければ `403` |
| S3 の直接 URL によるプロジェクトファイルの漏洩 | プロジェクトファイルの S3 URL はクライアントに渡さない。バックエンドのプロキシ経由のみとする |
| 任意ファイルの上書き | ストレージキーは UUID v4 で生成する |
| 超大型ファイルによる DoS | `RequestBodyLimitLayer` とストリーム中の実測値を `UPLOAD_MAX_SIZE_MB` から設定する |
| パストラバーサル（ローカル） | ストレージキーは UUID のみを使う。元ファイル名はメタデータのみとする |
| 共有トークンの総当たり | [公開共有のレートリミット](/features/drive/folders-and-sharing#公開共有のレートリミット)に書く |
| 共有経由の過剰アクセス | `viewer` の共有では削除・アップロードの API を `403` で止める |

## 認可

### ファイル本文のアクセス規則

テナント配下の管理 API はセッション認証または PAT 認証が必須である。`GET /v1/drive/files/{id}/content` は認証任意だが、取得にはテナント／プロジェクト権限または共有トークンが要る。`GET /v1/drive/share/{token}` とその `/files` は共有トークン自体を認証情報として扱う。

| ファイルの種類 | 閲覧できる人 |
|---|---|
| `project_id = NULL`（テナント一般ファイル） | テナント所属者、テナントオーナー、有効なフォルダ共有トークンの提示者 |
| `project_id = <id>`（プロジェクトファイル） | そのプロジェクトに入れる人、テナントオーナー、フォルダ共有権限を持つ利用者とトークン |

プロジェクトに入れるかは、ファイルの `tenant_id` に所属していることを先に確認したうえで、プロジェクトの公開規則で判定する。判定の詳細は[テナント / プロジェクト認可](https://github.com/koyori-app/task/blob/main/apps/backend/docs/tenant-project-authz.md)に書く。テナントに所属しないプロジェクト限定のゲストは、プロジェクトメンバーであるだけでは Drive へアクセスできない。

フォルダ共有は所属とは独立した明示的な付与なので、テナントから外しても失効しない。テナント一般ファイルの本文取得では利用者指定共有を見ず、テナント所属か共有トークンだけで判定する。プロジェクトファイルの本文は、セッションまたは PAT の認証と有効な利用者指定共有があれば、テナント外の受信者も取得できる。いずれも満たさない場合は `403 Forbidden` を返す。

### 判定の順序

ファイルへのアクセスは次の順に判定する。

1. 共有トークンの提示者は、テナント所属と独立して判定する。ファイルに `folder_id` があり、有効なトークンの共有があれば許可する
2. 認証済みの利用者は `read:drive` を持たなければ拒否する
3. テナントが 2FA を強制していれば、ここで確かめる。プロジェクトファイルの枝はテナントの所属判定を通らない
4. テナント一般ファイルは、テナント所属者またはオーナーだけに許可する。利用者指定共有は見ない
5. PAT のテナント・プロジェクトの束縛を、ファイル自身の値と突き合わせる
6. テナントオーナー、または「テナントに所属し、プロジェクトの公開規則を満たす人」に許可する
7. フォルダの利用者指定共有があれば許可する

`has_user_share` / `has_token_share` はファイルの `folder_id` からフォルダ階層を祖先方向へ辿り、いずれかのフォルダに有効な共有の行があれば `true` を返す。各階層を順に問い合わせる。空でない `token` を提示した場合はトークンの判定を優先し、無効・期限切れなら認証済みでも `403` を返す。

### PAT のスコープ

Drive に関わるスコープは次のとおりである。

| スコープ | 説明 |
|---|---|
| `read:project` | プロジェクトの読み取り |
| `write:project` | プロジェクトの作成・更新。削除はセッション専用 |
| `write:tenant` | テナントの設定変更。`read:tenant` を包含する |
| `api` | すべての `read:*` / `write:*` を包含する |
| `read_api` | すべての `read:*` を包含する |
| `read:drive` | ドライブのファイル・フォルダの一覧取得、ダウンロード、使用量の確認 |
| `write:drive` | ファイルのアップロード・削除・移動、フォルダの作成・削除・移動、共有の作成・取り消し。`read:drive` を包含する |

`read_api` は `read:drive` を、`api` は `read:drive` / `write:drive` と、クォータ設定に要る `write:tenant` を包含する。いずれもスコープの要件を満たすだけであり、テナント所属・プロジェクト権限・オーナー限定の判定は別に行う。

スコープは `apps/backend/crates/entity/src/scopes.rs` の `Scope` enum に定義する。包含関係は `Scope::implies` の網羅 match が一箇所で持ち、`has_scope` はそれを引くだけである。規則の一覧は [personal-access-tokens-authz.md](https://github.com/koyori-app/task/blob/main/apps/backend/docs/personal-access-tokens-authz.md) の「含意の規則」にある。

エンドポイントごとの必要なスコープは次のとおりである。

| メソッド | パス | スコープ | 備考 |
|---|---|---|---|
| GET | `/v1/tenants/{tenant_id}/drive/files` | `read:drive` | |
| POST | `/v1/tenants/{tenant_id}/drive/files` | `write:drive` | クォータの検証あり |
| GET | `/v1/tenants/{tenant_id}/drive/files/{id}` | `read:drive` | |
| PATCH | `/v1/tenants/{tenant_id}/drive/files/{id}` | `write:drive` | |
| PUT | `/v1/tenants/{tenant_id}/drive/files/{id}/content` | `write:drive` | テキスト本文の更新。クォータの検証あり |
| DELETE | `/v1/tenants/{tenant_id}/drive/files/{id}` | `write:drive` | |
| GET | `/v1/tenants/{tenant_id}/drive/files/{id}/tasks` | `read:drive` + `read:task` | 結び付いたタスクの一覧 |
| GET | `/v1/drive/files/{id}/content` | `read:drive` | 共有トークンの利用時はスコープ不要 |
| GET | `/v1/drive/files/{id}/content?token=` | スコープ不要 | 公開リンクのトークンで代替する |
| GET | `/v1/tenants/{tenant_id}/drive/usage` | `read:drive` | |
| PATCH | `/v1/tenants/{tenant_id}/drive/quota` | `write:tenant` | テナントオーナー限定 |
| GET | `/v1/tenants/{tenant_id}/drive/folders` | `read:drive` | |
| POST | `/v1/tenants/{tenant_id}/drive/folders` | `write:drive` | |
| PATCH | `/v1/tenants/{tenant_id}/drive/folders/{folder_id}` | `write:drive` | |
| DELETE | `/v1/tenants/{tenant_id}/drive/folders/{folder_id}` | `write:drive` | |
| GET | `/v1/tenants/{tenant_id}/drive/folders/{folder_id}/shares` | `read:drive` | |
| POST | `/v1/tenants/{tenant_id}/drive/folders/{folder_id}/shares` | `write:drive` | |

| GET | `/v1/drive/share/{token}` | スコープ不要 | 公開リンク（認証不要） |
| GET | `/v1/drive/share/{token}/files` | スコープ不要 | 公開リンク（認証不要） |

## 未実装と既知の制限

Drive 全体に効く差分は次のとおりである。機能ごとの差分は各ページの同じ名の節に書く。ここに記載した項目は期待する仕様ではなく、修正対象として追跡するための現状である。

| 優先度 | 項目 | 現状と影響 |
|---|---|---|
| 高 | ストレージ削除の非同期整合性 | 個別削除は DB の削除後のストレージエラーを無視し、プロジェクト／テナントの CASCADE 削除ではストレージの削除自体を行わない。孤児オブジェクトを回収する仕組みが要る |
| 中 | ストレージ種別の切り替え | DB に `storage_type` を保存するが、取得・削除は起動中の単一バックエンドだけを使う。`STORAGE_BACKEND` を変更すると、変更前のファイルを取得・削除できない |
| 低 | 使われない S3 公開 URL の設定 | 実装は `S3_PUBLIC_BASE_URL` を読み込むが、全ファイルをプロキシ配信するので値は使われない |
| なし | フロントエンド | Drive のページ、ファイルブラウザ、クォータ、共有の UI が無い。ドキュメント画面とタスク添付の UI だけがある |

実装の順序は次のとおりである。バックエンドの基本 API と階層変更の境界の保護は揃っているので、残るストレージ・共有の差分を直し、その契約をテストで固定してからフロントエンドへ進む。

| 順序 | 内容 | 完了条件 |
|---|---|---|
| 1 | ストレージ削除の回収経路の追加 | 個別・プロジェクト・テナントの削除と失敗時の再試行をテストできる |
| 2 | フォルダ・共有受信者向けの一覧 API の整理 | プロジェクト権限と共有範囲に沿って、子フォルダを含む一覧を提供できる |
| 3 | ストレージバックエンドの移行方針の決定 | `storage_type` ごとに取得するか、切り替え前の移行を必須化する |
| 4 | フロントエンドの実装 | ファイルブラウザ、クォータ、共有の UI を提供する |
