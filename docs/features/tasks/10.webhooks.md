## 1. データモデル

### `webhooks`

| カラム | 型 | 制約 | 説明 |
|--------|-----|------|------|
| `id` | UUID | PK | |
| `project_id` | UUID | NOT NULL, FK→projects CASCADE | |
| `url` | VARCHAR(2048) | NOT NULL | 送信先 URL（§5.2 の SSRF 検証を通ったもの） |
| `secret_enc` | VARCHAR | NOT NULL | HMAC-SHA256 署名用シークレットを暗号化した値（`auth_core::crypto::encrypt_token`、鍵は `TOTP_ENCRYPTION_KEY`）。平文は作成時の応答でだけ返す |
| `events` | VARCHAR[] | NOT NULL | 購読するイベント名（§3。1 つ以上） |
| `format` | VARCHAR | NOT NULL DEFAULT `'json'`, CHECK `json` / `discord` | 本文の形（§4.4） |
| `is_active` | BOOLEAN | NOT NULL DEFAULT true | 連続失敗で自動 false（§5.1） |
| `failure_streak` | SMALLINT | NOT NULL DEFAULT 0 | 打ち止めになった配信の連続数。成功で 0、`is_active` を true に戻すと 0 |
| `created_by` | UUID | NOT NULL, FK→users | |
| `created_at` | TIMESTAMPTZ | NOT NULL DEFAULT now() | |

### `webhook_deliveries`

配信の行そのものが送信待ちの行列（outbox）を兼ねる。

| カラム | 型 | 制約 | 説明 |
|--------|-----|------|------|
| `id` | UUID | PK | `X-Task-Delivery` ヘッダの値 |
| `webhook_id` | UUID | NOT NULL, FK→webhooks CASCADE | |
| `event` | VARCHAR | NOT NULL | |
| `payload` | JSONB | NOT NULL | 送信ペイロード（`format=json` の本文そのもの） |
| `status_code` | INT | NULLABLE | 最後の試行の HTTP レスポンスコード（接続失敗なら NULL） |
| `attempt` | SMALLINT | NOT NULL DEFAULT 0 | 試行した回数（最大 5） |
| `next_attempt_at` | TIMESTAMPTZ | NULLABLE | 次に試す時刻。NULL = 完了（成功・打ち止め・Webhook 停止） |
| `last_error` | TEXT | NULLABLE | 最後の失敗の理由 |
| `delivered_at` | TIMESTAMPTZ | NULLABLE | 成功時のみ |
| `created_at` | TIMESTAMPTZ | NOT NULL DEFAULT now() | |

## 2. マイグレーション

`m20260922020000_webhooks.rs`。

```sql
CREATE TABLE webhooks (
    id UUID PRIMARY KEY,
    project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    url VARCHAR(2048) NOT NULL,
    secret_enc VARCHAR NOT NULL,
    events VARCHAR[] NOT NULL,
    format VARCHAR NOT NULL DEFAULT 'json',
    is_active BOOLEAN NOT NULL DEFAULT true,
    failure_streak SMALLINT NOT NULL DEFAULT 0,
    created_by UUID NOT NULL REFERENCES users(id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT chk_webhooks_format CHECK (format IN ('json', 'discord'))
);
CREATE INDEX idx_webhooks_project ON webhooks(project_id);

CREATE TABLE webhook_deliveries (
    id UUID PRIMARY KEY,
    webhook_id UUID NOT NULL REFERENCES webhooks(id) ON DELETE CASCADE,
    event VARCHAR NOT NULL,
    payload JSONB NOT NULL,
    status_code INT,
    attempt SMALLINT NOT NULL DEFAULT 0,
    next_attempt_at TIMESTAMPTZ,
    last_error TEXT,
    delivered_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_webhook_deliveries_webhook ON webhook_deliveries(webhook_id, created_at DESC);
CREATE INDEX idx_webhook_deliveries_pending ON webhook_deliveries(next_attempt_at)
    WHERE next_attempt_at IS NOT NULL;
CREATE INDEX idx_webhook_deliveries_created ON webhook_deliveries(created_at);
```

| `review.finding_changed` | 指摘の状態遷移 | 実装済み |
| `task.updated` | タスクのフィールド変更（差分のみ） | 未実装 |
| `task.deleted` | タスク削除 | 未実装 |
| `task.archived` / `task.unarchived` | アーカイブ操作 | 未実装 |
| `github.pr_linked` | PR リンク追加 | 未実装 |
| `github.pr_merged` | PR マージ | 未実装 |
| `sprint.started` / `sprint.completed` | スプリント状態変化 | 未実装 |

未実装のイベントは購読できない（作成・更新で 400）。

配信はイベントを起こした操作と**同じトランザクション**で `webhook_deliveries` に積む
（`service::webhooks::emit`）。操作が巻き戻れば配信も残らない。止まっている Webhook
（`is_active = false`）には積まない。

## 4. ペイロード仕様

### 4.1 リクエストヘッダー

```text
Content-Type: application/json
X-Task-Event: task.created
X-Task-Delivery: <webhook_deliveries.id>
X-Task-Signature: sha256=<HMAC-SHA256-hex>   ← format=json のときだけ
```

署名検証（受信側）:

```text
"sha256=" + hex(HMAC-SHA256(secret, raw_request_body)) == X-Task-Signature の値
```

同じ配信の再試行は `X-Task-Delivery` が同じ。手動再送（§6）は新しい配信なので別の値になる。

### 4.2 共通フィールド

すべてのイベントが次を持つ。

```json
{
  "event": "task.created",
  "timestamp": "2026-05-27T10:00:00Z",
  "project_id": "uuid",
  "project": { "id": "uuid", "key": "ENG", "name": "Engineering" },
  "actor": { "id": "uuid", "username": "alice" }
}
```

### 4.3 イベント固有のフィールド

`task.created`:

```json
{
  "task": {
    "id": "uuid", "seq_id": 42,
    "title": "OAuth 対応を実装する",
    "priority": "high",
    "status": "Backlog",
    "assignees": [{ "user_id": "uuid", "role": "primary" }],
    "hard_deadline": "2026-06-10T00:00:00Z",
    "created_by": "uuid"
  }
}
```

`comment.created`:

```json
{
  "task": { "id": "uuid", "seq_id": 42, "title": "OAuth 対応を実装する" },
  "comment": { "id": "uuid", "author": "alice", "body": "本文" }
}
```

`review.round_created` / `review.finding_changed` は in-app 通知
（`review_round_created` / `review_finding_changed`）の payload と同じ中身
（`service::notifications::review_round_payload` / `review_finding_payload` を共有）。
`actor` だけは共通フィールドの object で上書きされる（in-app では名前の文字列）。

`review.round_created`:

```json
{
  "review_id": "uuid", "repo": "owner/name", "pr_number": 618, "round": 2,
  "head_sha": "60cdd77…", "reviewer": "alice",
  "counts": { "high": 1, "medium": 2, "low": 0, "nit": 0 },
  "summary_excerpt": "総評の先頭 200 文字"
}
```

`review.finding_changed`:

```json
{
  "review_id": "uuid", "finding_id": "uuid", "repo": "owner/name", "pr_number": 618, "round": 2,
  "title": "指摘のタイトル", "severity": "high", "from": "open", "to": "fixed", "note": null
}
```

### 4.4 `format=discord`

Discord の Incoming Webhook URL をそのまま登録できる。本文は Discord の形に変える。

```json
{
  "content": "[Koyori] PR #618 のレビュー R2（high 1 / medium 2 / low 0 / nit 0）",
  "embeds": [{
    "title": "review.round_created",
    "description": "alice が PR #618 のレビュー R2 を起票しました。…",
    "fields": [
      { "name": "プロジェクト", "value": "Engineering", "inline": true },
      { "name": "実行者", "value": "alice", "inline": true }
    ]
  }]
}
```

- レビュー系の要約は通知メールの件名・本文 1 行目と同じ文言（`service::notification_email::subject_and_line`）
- `content` は 2000 文字、`description` は 4096 文字で切る（Discord の上限）
- 署名ヘッダは付けない（Discord は検証しない。URL 自体が秘密）

## 5. 配信

### 5.1 掃き出しループとリトライ

`job::webhook_delivery` の掃き出しループが 10 秒ごとに、`next_attempt_at <= now()` の配信を
最大 50 件拾って送る。1 件ごとに短いトランザクションで `FOR UPDATE SKIP LOCKED` を取り直し、
送信結果をその行に書いて commit する（複数インスタンスでも同じ配信を二重に送らない）。

- 1 回の送信の timeout は 10 秒。リダイレクトは追わない（3xx は失敗）
- `2xx`: `delivered_at` を立てて完了。Webhook の `failure_streak` を 0 に戻す
- それ以外・接続失敗: `attempt` を進め、次の試行を予約する
  - 1 回目: 即時 / 2 回目: 30s / 3 回目: 5m / 4 回目: 30m / 5 回目: 2h
  - 5 回失敗したら打ち止め（`next_attempt_at = NULL`）。Webhook の `failure_streak` を 1 増やす
- `failure_streak` が 5（打ち止めが 5 本連続）になったら `webhooks.is_active = false`
  - **未実装**: テナントオーナーへのメール通知。通知メール（[通知 §3](/features/tasks/notifications)）は
    利用者ごとの購読で、運用者宛ての連絡とは別物のため
- 止まった Webhook の送信待ちは送らずに完了にする（`last_error = "webhook is inactive"`）
- 配信履歴は 90 日で消す（同じループが 1 時間に 1 回 `created_at` で掃除する）

### 5.2 送信先の検証（SSRF）

`service::webhooks::resolve_url` で作成・更新時と**送信の直前**に名前解決し、全アドレスを検証する
（DNS の向き先は登録後に変えられるため）。送信時はその検証済み IP に接続を固定し、
接続時の再解決を防ぐ。元のホスト名は Host ヘッダと TLS の検証に使う。

- `https` 必須（`http` は localhost のみ）
- private / link-local / メタデータ（`169.254.169.254`）宛てと、それらへ解決される名前は拒否
- loopback（`localhost` / `127.0.0.0/8` / `::1`、IPv4-mapped IPv6 と DNS の解決先も含む）は
  既定では拒否。開発・テストでのみ `WEBHOOK_ALLOW_LOOPBACK=true` を明示して許可する
- 作成・更新時の拒否は 400。送信時の拒否は配信の失敗として数える
- リダイレクトは追わず、環境変数の HTTP プロキシも使用しない

## 6. API

`/v1/tenants/{tenant_id}/projects/{project_id}/webhooks` 配下。

| メソッド | パス | 必要スコープ | 説明 |
|---------|------|-------------|------|
| `GET` | `/` | `read:project` | 一覧（`secret` は返さない） |
| `POST` | `/` | `admin:project` + プロジェクト Admin | 作成（`secret` は作成時のみ平文返却） |
| `PUT` | `/{id}` | `admin:project` + プロジェクト Admin | 更新。有効 / 無効の切り替えもこれ |
| `DELETE` | `/{id}` | `admin:project` + プロジェクト Admin | 削除（配信履歴も消える） |
| `GET` | `/{id}/deliveries?limit=` | `read:project` | 配信履歴（新しい順、既定 50・最大 100） |
| `POST` | `/{id}/deliveries/{did}/redeliver` | `admin:project` + プロジェクト Admin | 手動再送。同じ payload で新しい配信を積む（元の行は変えない） |

- 「プロジェクト Admin」はプロジェクトの `Admin` ロールかテナントオーナー（`require_project_admin`）
- 他プロジェクトの Webhook / 配信の ID は 404
- `format=discord` の URL は認証情報を含むため、一覧では `[redacted]` を返す。
  完全な URL は管理権限が必要な作成・更新の応答でのみ返す。配信エラーにも URL は残さない
- 当初案の `POST /{id}/toggle` は作らない。`PUT` の `is_active` で代替する。
  `is_active` を true に戻すと `failure_streak` も 0 に戻る

`POST /webhooks` リクエスト:

```json
{
  "url": "https://example.com/webhook",
  "secret": "my-secret-token-16+",
  "events": ["task.created", "review.round_created"],
  "format": "json"
}
```

| フィールド | 検証 |
|-----------|------|
| `url` | 2048 文字以内。§5.2 |
| `secret` | 16 文字以上 |
| `events` | §3 の実装済みイベントの部分集合。空は不可 |
| `format` | `json`（既定）/ `discord` |

`PUT /webhooks/{id}` は `url` / `secret` / `events` / `format` / `is_active` のうち指定したものだけ変える。

## 7. フロントエンド

実装済み: プロジェクト設定 > Webhook（`?section=webhooks`。`WebhooksSection.vue` /
`WebhookFormDialog.vue`）。

- 一覧: URL・形式（JSON / Discord）・購読イベント・状態（有効 / 無効）。`failure_streak > 0` なら
  「連続失敗 N 回」、連続失敗で止まったもの（`is_active = false` かつ `failure_streak >= 5`）は
  「連続失敗で停止」と表示する
- 作成・編集はダイアログ。secret は作成時は必須（16 文字以上）、編集時は空欄なら変更しない。
  編集は変えたフィールドだけ `PUT` する。一覧が `[redacted]` を返す Discord の URL は
  欄に出さず、secret と同じく空欄なら変更しない
- secret は作成直後に同じダイアログで一度だけ表示し、コピーできる。閉じたら再表示できない
  （API も返さない。失くしたら編集で新しい値に差し替える）
- 行の操作: 編集 / 無効にする・有効にする（`PUT { is_active }`。有効に戻すと連続失敗も 0 に戻る）/
  削除（確認ダイアログ）/ 配信履歴
- 配信履歴は行の下に展開し、新しい順に 20 件を出す。結果は「成功 (HTTP N)」「再試行待ち」
  「失敗 (n 回)」+ 最後のエラー。payload は折りたたみで見られる。「再送」は §6 の redeliver を
  呼び、新しい配信が履歴の先頭に増える
- 変更系の 403 は「この操作にはプロジェクトの管理者権限が必要です」と出す。ボタンは権限に
  関わらず表示する

## 8. 決定事項

- 配信はジョブキュー（apalis）ではなく配信の行を outbox にした掃き出しループ。イベントを起こす
  service からは apalis へ積めない（依存の向きが service → job）ため、通知メールと同じ形にした
- secret の暗号化鍵は `TOTP_ENCRYPTION_KEY`。起動に必須の鍵なので、GitHub App を設定していない
  環境でも Webhook を使える（`GITHUB_TOKEN_ENCRYPTION_KEY` は GitHub App 設定時にしか無い）
- 送信は共有の HTTP クライアントではなくリダイレクトを追わない専用のクライアントで行う
  （検証済みの URL から private な宛先へ 302 で飛ばされるのを防ぐ）
