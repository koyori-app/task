## 1. 概要

タスク管理の基盤となる機能で、他のタスク機能はこのページのテーブルと API の上に作る。

含む機能:

- タスク CRUD + プロジェクト内連番 ID（`KEY-N` 形式。例: `ENG-42`）
- カスタムステータス（プロジェクト単位）
- 担当者
- 優先順位・締切（Soft / Hard）・開始予定日・進捗率
- 親子タスク・ブロッキング依存関係
- ラベル（プロジェクト単位 + export / import）
- マイルストーン

### 2.2 `project_statuses`

```rust
pub struct Model {
    pub id: Uuid,
    pub project_id: Uuid,
    pub name: String,
    pub color: String,        // hex (#3b82f6)
    pub position: i16,        // 表示順
    pub is_default: bool,     // 既定のステータス（プロジェクト内で 1 つ）
    pub is_done_state: bool,  // このステータス = 完了とみなす（複数可）
    pub is_default_done: bool, // 「完了にする」操作の移動先（完了のうち 1 つのみ）
    pub created_at: DateTimeUtc,
}
```

| カラム | 型 | 制約 |
|--------|-----|------|
| `id` | UUID | PK |
| `project_id` | UUID | NOT NULL, FK→projects CASCADE |
| `name` | VARCHAR(100) | NOT NULL |
| `color` | VARCHAR(7) | NOT NULL |
| `position` | SMALLINT | NOT NULL |
| `is_default` | BOOLEAN | NOT NULL DEFAULT false |
| `is_done_state` | BOOLEAN | NOT NULL DEFAULT false |
| `is_default_done` | BOOLEAN | NOT NULL DEFAULT false |
| `created_at` | TIMESTAMPTZ | NOT NULL DEFAULT now() |
| — | — | UNIQUE(project_id, name) |

通常のプロジェクトを作ると `Backlog` / `Todo`（`is_default`）/ `In Progress` / `Done`（`is_done_state` と `is_default_done`）の 4 つを自動で挿入する。個人プロジェクトは `Todo`（`is_default`）と `Done` の 2 つである。タスク作成 API は `status_id` を必須としており、`is_default` を自動では補わない（既定値を使うのはクライアント側である）。

完了ステータスは複数持てる（`Done` と `No Planning` のように）。そのうち 1 つに `is_default_done` を付け、CLI の `tasks complete`・タスク詳細の完了ボタン・GitHub Issue の close 同期はここへ移す。印が無いプロジェクトでは並び順で最初の完了ステータスを使う。

- `is_default_done` は完了ステータスにしか付けられず、付け替えると他からは自動で外れる。付いているものを直接 `false` にする更新は 400 になる
- 完了ステータスが 1 つも無い状態にはできない（最後の 1 つは `is_done_state` を外せず、削除もできない）
- 完了ステータスを外したり削除したりして `is_default_done` の持ち主が消えると、並び順で最初の完了ステータスへ付け直す
- 完了を外したステータスにあるタスクは `completed_at` が消える。完了にしたステータスにあるタスクと、完了へ移したタスクには `completed_at` が入る（既に値があれば保つ）
- `is_default` のステータスは削除できない（400）

| カラム | 型 | 制約 |
|--------|-----|------|
| `id` | UUID | PK |

| `created_at` | TIMESTAMPTZ | NOT NULL DEFAULT now() |
| — | — | UNIQUE(blocker_task_id, blocked_task_id) |
| — | — | CHECK(blocker_task_id <> blocked_task_id) |

循環依存はリレーション追加時にサーバー側で BFS を行って検出し、`409 Conflict` を返す。トランザクションを SERIALIZABLE にして、逆向きの追加が同時に走って検出をすり抜けることを防いでいる。親子関係（`parent_task_id`）の循環も更新時に検出する。

## 3. マイグレーション

スキーマは `apps/backend/migration` の `m20260520000000_initial_schema` にまとまっており、増分は別のマイグレーションである。

```sql
-- プロジェクトキー（KEY-N 形式に使用）
CREATE TABLE projects (
    -- 他のカラムは省略
    key VARCHAR(10) NOT NULL,
    CONSTRAINT projects_key_format CHECK (key ~ '^[A-Z][A-Z0-9]{1,9}$')
);
CREATE UNIQUE INDEX projects_key_tenant_unique ON projects(tenant_id, key);
```

`key` はテナント内で一意の英大文字識別子（例: `ENG`、`BACK`、`WEB`）である。プロジェクト作成 API で指定すれば、その値を検証して使う（重複はエラー）。省略するとプロジェクト名の英数字を大文字にして先頭 10 文字を取り（例: "Backend API" → `BACKENDAPI`）、英数字が足りないか形式に合わなければ `PROJ` にする。自動生成のキーが重複したら、先頭 6 文字とランダムな 4 文字に作り直す。

```sql
CREATE TABLE project_task_counters (
    project_id UUID PRIMARY KEY REFERENCES projects(id) ON DELETE CASCADE,
    last_seq INT NOT NULL DEFAULT 0
);

CREATE TABLE project_statuses (
    id UUID PRIMARY KEY,
    project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    name VARCHAR(100) NOT NULL,
    color VARCHAR(7) NOT NULL,
    position SMALLINT NOT NULL,
    is_default BOOLEAN NOT NULL DEFAULT false,
    is_done_state BOOLEAN NOT NULL DEFAULT false,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (project_id, name)
);

CREATE TABLE milestones (
    id UUID PRIMARY KEY,
    project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    name VARCHAR(255) NOT NULL,
    description TEXT,
    due_date DATE NOT NULL,
    created_by UUID NOT NULL REFERENCES users(id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE tasks (
    id UUID PRIMARY KEY,
    project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    seq_id INT NOT NULL,
    title VARCHAR(255) NOT NULL,
    description TEXT,
    status_id UUID NOT NULL REFERENCES project_statuses(id),
    priority VARCHAR NOT NULL DEFAULT 'medium',
    progress_pct SMALLINT NOT NULL DEFAULT 0 CHECK (progress_pct BETWEEN 0 AND 100),
    parent_task_id UUID REFERENCES tasks(id) ON DELETE SET NULL,
    milestone_id UUID REFERENCES milestones(id) ON DELETE SET NULL,
    soft_deadline TIMESTAMPTZ,
    hard_deadline TIMESTAMPTZ,
    estimated_minutes INT CHECK (estimated_minutes > 0),
    is_archived BOOLEAN NOT NULL DEFAULT false,
    created_by UUID NOT NULL REFERENCES users(id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at TIMESTAMPTZ,
    sprint_id UUID REFERENCES sprints(id) ON DELETE SET NULL,
    completed_at TIMESTAMPTZ,
    UNIQUE (project_id, seq_id),
    CONSTRAINT soft_before_hard CHECK (
        soft_deadline IS NULL OR hard_deadline IS NULL OR soft_deadline <= hard_deadline
    )
);

CREATE TABLE task_assignees (
    id UUID PRIMARY KEY,
    task_id UUID NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role VARCHAR NOT NULL DEFAULT 'secondary',
    assigned_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX uq_task_assignees_task_user ON task_assignees(task_id, user_id);

CREATE TABLE task_relations (
    id UUID PRIMARY KEY,
    blocker_task_id UUID NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    blocked_task_id UUID NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (blocker_task_id, blocked_task_id),
    CHECK (blocker_task_id <> blocked_task_id)
);

CREATE TABLE labels (
    id UUID PRIMARY KEY,
    name VARCHAR NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    color VARCHAR NOT NULL,
    icon_url TEXT,
    project_id UUID REFERENCES projects(id) ON DELETE CASCADE
);
CREATE UNIQUE INDEX labels_project_name_unique ON labels(project_id, name);

CREATE TABLE task_labels (
    task_id UUID NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    label_id UUID NOT NULL REFERENCES labels(id) ON DELETE CASCADE,
    PRIMARY KEY (task_id, label_id)
);

CREATE INDEX idx_tasks_project ON tasks(project_id) WHERE deleted_at IS NULL;
CREATE INDEX idx_tasks_status ON tasks(status_id);
CREATE INDEX idx_tasks_parent ON tasks(parent_task_id) WHERE parent_task_id IS NOT NULL;
CREATE INDEX idx_tasks_sprint ON tasks(sprint_id) WHERE sprint_id IS NOT NULL;
CREATE INDEX idx_task_relations_blocked_task_id ON task_relations(blocked_task_id);
CREATE INDEX idx_task_labels_label_id ON task_labels(label_id);
```

## 4. API

URL 基底パス: `/v1/tenants/{tenant_id}/projects/{project_id}`

### 4.1 タスク

| メソッド | パス | 説明 |
|---------|------|------|
| `GET` | `/tasks` | 一覧（フィルター・ソート・ページング） |
| `POST` | `/tasks` | 作成 |
| `GET` | `/tasks/{id}` | 取得（UUID または `KEY-N`、例: `ENG-42`） |
| `PUT` | `/tasks/{id}` | 更新（全フィールド optional） |
| `DELETE` | `/tasks/{id}` | ソフトデリート |
| `POST` | `/tasks/{id}/archive` | アーカイブ |
| `POST` | `/tasks/{id}/unarchive` | アーカイブ解除 |

#### GET `/tasks` クエリパラメータ

| パラメータ | 型 | 説明 |
|-----------|-----|------|
| `status_id` | UUID? | |
| `priority` | string? | DB 値（`high` など）。不明な値は 400 |
| `assignee_id` | UUID? | |
| `created_by` | UUID? | 指定ユーザーが作成したタスクのみ |
| `label_id` | UUID? | 指定ラベルが付与されたタスクのみ |
| `milestone_id` | UUID? | |
| `sprint_id` | UUID? | |
| `parent_task_id` | UUID? | サブタスク一覧 |
| `planned_start_from` | date? | 開始予定日がこの日以降（`YYYY-MM-DD`、両端含む） |
| `planned_start_to` | date? | 開始予定日がこの日以前（両端含む）。`from > to` は 400。どちらかを指定すると開始予定日が未設定のタスクは除外 |
| `root_only` | bool | デフォルト false。親が同じ絞り込みの結果に含まれないタスクだけを返す（List 表示が使う） |
| `is_archived` | bool | デフォルト false |
| `sort` | string | `created_at_desc`（デフォルト）、または `title` / `assignee` / `priority` / `deadline` に `_asc` / `_desc` を付けた値 |
| `limit` | u32 | デフォルト 50、1〜200 に丸める |
| `offset` | u32 | ページ番号で飛ぶ一覧（表形式）が使う |
| `cursor` | string? | 前のページの `next_cursor`。`offset` と同時指定は 400。カーソルは `sort` ごとに別物である |

続きを読み足す一覧が `offset` ではなくカーソルを使うのは、取得の間にタスクが増減すると `offset` の境界がずれ、境界の行がどちらのページにも出なくなるためである。

#### POST `/tasks` リクエスト

`title` と `status_id` が必須である。`priority` は JSON の値（`High` など。[概要](/features/tasks)）で送る。`custom_field_values` は[カスタムフィールド](/features/tasks/custom-fields)の値である。

```json
{
  "title": "OAuth 対応を実装する",
  "description": "## 概要\nGitHub Apps を使って…",
  "priority": "High",
  "status_id": "uuid",
  "progress_pct": 0,
  "soft_deadline": "2026-06-01T00:00:00Z",
  "hard_deadline": "2026-06-10T00:00:00Z",
  "planned_start_on": "2026-05-28",
  "estimated_minutes": 180,
  "assignees": [{ "user_id": "uuid", "role": "primary" }],
  "label_ids": ["uuid"],
  "milestone_id": "uuid",
  "sprint_id": "uuid",
  "parent_task_id": null,
  "custom_field_values": [{ "field_id": "uuid", "value": "5" }]
}
```

作成と更新の応答は `GET /tasks/{id}` と同じ形（`TaskDetailResponse`）で、`TaskResponse` のフィールドに `custom_field_values` と `mentions` を足している。

`PUT /tasks/{id}` は値をクリアするために `clear_description` / `clear_parent_task_id` / `clear_milestone_id` / `clear_sprint_id` / `clear_soft_deadline` / `clear_hard_deadline` / `clear_planned_start_on` / `clear_estimated_minutes` を持つ。`label_ids` は集合の置き換え、`add_label_ids` / `remove_label_ids` は差分で、`assignees` は担当者集合の置き換え（既存の担当者の役割は保つ）である。完了済みのスプリントへの割り当ては 409 になる。

#### GET `/tasks` レスポンス

ステータスとユーザーは ID または要約で返し、`subtask_count` は持たない。

```json
{
  "tasks": [{
    "id": "uuid", "project_id": "uuid", "seq_id": 42,
    "title": "OAuth 対応を実装する",
    "description": "## 概要\n…",
    "status_id": "uuid",
    "priority": "High", "progress_pct": 40,
    "parent_task_id": null, "milestone_id": null, "sprint_id": null,
    "assignees": [{ "role": "primary", "user": { "id": "uuid", "username": "alice", "avatar_url": null } }],
    "labels": [],
    "soft_deadline": "2026-06-01T00:00:00Z",
    "hard_deadline": "2026-06-10T00:00:00Z",
    "planned_start_on": "2026-05-28",
    "estimated_minutes": 180,
    "is_archived": false,
    "created_by": { "id": "uuid", "username": "alice", "avatar_url": null },
    "created_at": "2026-05-27T10:00:00Z",
    "updated_at": "2026-05-27T10:00:00Z",
    "completed_at": null,
    "deleted_at": null
  }],
  "total": 42,
  "next_cursor": null
}
```

`total` は絞り込み後の総数で、件数の表示とページ番号の算出に使う。「まだ残っているか」の判断には `next_cursor` を使う（総数は取得中に動くので、比較では終わらないことがある）。

### 4.2 担当者

| メソッド | パス | 説明 |
|---------|------|------|
| `GET` | `/tasks/{id}/assignees` | 一覧 |
| `POST` | `/tasks/{id}/assignees` | 追加 `{ "user_id": "uuid", "role": "primary" }` |
| `PUT` | `/tasks/{id}/assignees/{user_id}` | ロール変更 |
| `DELETE` | `/tasks/{id}/assignees/{user_id}` | 削除 |

担当者欄（タスク作成ダイアログ・タスク詳細・一覧の行）は、候補の後ろに部署・チームの行を出す。選ぶとその部署・チームの候補全員を担当者に加える。API は利用者ごとに送る（作成は `assignees` に全員を載せ、作成後は 1 人ずつ `POST`）。部署・チームは `tenant_members` の自由記述をそのまま使うので、表記が違えば別の行になる。

### 4.3 依存関係

| メソッド | パス | 説明 |
|---------|------|------|
| `GET` | `/tasks/{id}/relations` | 一覧（parent / subtasks / blocks / blocked_by） |
| `POST` | `/tasks/{id}/relations` | 追加 |
| `DELETE` | `/tasks/{id}/relations/{relation_id}` | 削除 |

`POST` リクエストは **どちらのタスクからでも設定できる**。

| `type` | 意味 |
|--------|------|
| `"blocks"` | 現タスクが `target` をブロック |
| `"blocked_by"` | 現タスクは `target` にブロックされている |

```json
{ "type": "blocks", "target_task_id": "uuid" }
```

```json
// 同じ関係を反対側から設定する場合（結果は同一レコード）
{ "type": "blocked_by", "target_task_id": "uuid" }
```

`target_task_id` は同じプロジェクトのタスクの UUID に限る。同じ関係の重複と循環は 409 になる。

`GET` レスポンスの各要素は `TaskResponse` の全フィールドで、`blocks` と `blocked_by` にはさらに `relation_id` が付く。

```json
{
  "parent": null,
  "subtasks": [{ "id": "uuid", "seq_id": 60, "title": "..." }],

  "blocked_by": [{ "relation_id": "uuid", "id": "uuid", "seq_id": 38, "title": "..." }]
```

### 4.4 カスタムステータス

| メソッド | パス | 説明 |
|---------|------|------|
| `GET` | `/statuses` | 一覧（position 順） |
| `POST` | `/statuses` | 作成 |
| `PUT` | `/statuses/{id}` | 更新 |
| `PUT` | `/statuses/reorder` | 並び順一括更新 `{ "ids": ["uuid1", "uuid2"] }`。プロジェクトの全ステータスを過不足なく渡す（違えば 400） |

### 4.5 マイルストーン

| メソッド | パス | 説明 |
|---------|------|------|
| `GET` | `/milestones` | 一覧 |
| `POST` | `/milestones` | 作成 |
| `GET` | `/milestones/{id}` | 取得（完了率含む） |
| `PUT` | `/milestones/{id}` | 更新 |
| `DELETE` | `/milestones/{id}` | 削除（タスクの `milestone_id` は NULL リセット） |

`GET /milestones/{id}` レスポンス:

```json
{
  "id": "uuid", "project_id": "uuid", "name": "v2.0 リリース",
  "description": null, "due_date": "2026-07-01",
  "created_by": "uuid", "created_at": "…", "updated_at": "…",
  "progress_pct": 33,
  "task_counts": { "total": 12, "done": 4 }
}
```

`progress_pct` は完了ステータスにあるタスクの割合を整数に切り捨てた値で、削除済みのタスクは数えない。

## 5. アクセス制御

| 操作 | スコープ | 権限 |
|------|---------|------|
| タスク閲覧 / 作成 / 更新 / アーカイブ | `read:task` / `write:task` | プロジェクトに入れる人 or テナントオーナー |
| タスク削除（ソフト） | `write:task` | 作成者 or テナントオーナー |
| ステータス / ラベル管理 | `write:task` | プロジェクトに入れる人 or テナントオーナー |
| マイルストーン管理 | `read:milestone` / `write:milestone` | プロジェクトに入れる人 or テナントオーナー |

「プロジェクトに入れる人」は、テナントの所属を継承した人と、そのプロジェクトに明示 ACE（`project_members` の行）を持つ人である。プロジェクトにメンバーを 1 人も指定していなければテナントメンバー全員が入れ、指定があれば明示 ACE を持つ人だけが入れる。明示 ACE はテナント所属と独立に残るので、テナントに行が無い人でも明示 ACE のあるプロジェクトには客分として入れる（テナント全体には入れない）。判定の詳細は [テナント / プロジェクト認可](https://github.com/koyori-app/task/blob/main/apps/backend/docs/tenant-project-authz.md) を参照。

一覧の List 表示はステータスごとにタスクをグループにして並べ、行をドラッグして別のグループへ移すとステータスが変わる。広い画面では一覧の右に詳細を開く。サブタスクは親の行の配下に描く。

未実装のものは次のとおりである。

- **カンバンボード**: カスタムステータスを列にして、ドラッグでステータス変更と列の並び替えを行う案がある。保存済みビューの `view_type` には `board` があるが、それを描く画面は無い
- **マイルストーン管理画面**: マイルストーンは API で作成する。画面ではカレンダーの最上段に期日の旗を出すだけである
- **依存関係のグラフ表示**: タスク詳細にサブタスクのパネルはあるが、ブロッキング関係を図にして見せる画面は無い

### キーボードショートカット

修飾キー無しの単打キーで操作する（`composables/useKeyboardShortcuts.ts`）。Shift の有無は区別しない。

| キー | 画面 | 動作 |
|---|---|---|
| `T` | タスク一覧（`tasks/+Page.vue`） | タスク作成モーダルを開く。一覧本体が表示されていないとき（読み込み中・エラー・テナント／プロジェクト未解決）は何もしない |
| `T` | ホーム（`HomeDashboard.vue`） | タスク作成モーダルを開く。作成ボタンが押せないとき（プロジェクト 0 件・取得失敗）は何もしない |
| `T` | ドキュメント詳細（`DocumentDetail.vue`） | 選択範囲をタイトルにしてタスク作成ダイアログを開く。「タスクを作成」ボタンが出ていないとき（読み込み中・エラー・対象外・編集中）は何もしない |

次のときは発火しない。

- 入力中（`input` / `textarea` / `select` / `contenteditable` の中）
- IME 変換中（`isComposing` または `keyCode` 229）
- ダイアログが開いている（`[role="dialog"]` / `dialog[open]` がある）。タスク詳細オーバーレイや確認ダイアログの上に重ねない
- 修飾キー付き（Ctrl / ⌘ / Alt）。ブラウザ・OS・既存の ⌘B / ⌘S と衝突させない
- キーの押しっぱなし（`repeat`）・他の処理が既に `preventDefault` したもの

## 7. 決定事項

| 項目 | 決定内容 |
|------|---------|
| 削除方式 | ソフトデリート（`deleted_at`）。物理削除の API は無い |
| ステータス | プロジェクト単位のカスタムステータス。ハードコードしない |
| 連番 ID | `SELECT FOR UPDATE` でアトミック採番。`KEY-N` 形式で表示（例: `ENG-42`） |
| ラベルスコープ | `project_id` でプロジェクト単位にする |
| 開始予定日 `planned_start_on` | DATE・NULL 可。更新は `planned_start_on` と `clear_planned_start_on`（同時指定は解除が優先、`clear_soft_deadline` と同じ）。Soft 締切との前後関係は検証しない（DB の CHECK もサーバーの検証も持たない）。計画用の値で前後が逆でも壊れるものがなく、締切は TIMESTAMPTZ のため日付との比較がタイムゾーン次第で正しい組を弾いてしまうため。変更は `planned_start_changed` 履歴に記録する |
| 親タスクの変更 | `PUT /tasks/{id}` の `parent_task_id`（設定・変更）と `clear_parent_task_id`（解除）。UI はタスク詳細のサブタスク欄（ページ・オーバーレイ・右ペイン共通）で、同じプロジェクトのタスクをキーまたはタイトルで検索して選ぶ。自分自身・現在の親・直下の子は候補から除き、深い子孫を選ぶと backend の 409 を理由つきで表示する |
| 説明文 `description` の上限 | 100,000 文字（バイトではなく文字で数える。`payload::tasks::MAX_DESCRIPTION_LEN`）。作成・更新で超過は 400。タスク詳細の SSR は Markdown を同期で描画するため、長大な本文で server プロセスを塞がないようにする。上限前に保存された超過行は移行せず、本文を送らない更新はそのまま通る。SSR は同じ値を超える本文を描画せずプレーン表示にする |
