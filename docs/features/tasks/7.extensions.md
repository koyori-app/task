## 1. 全文検索

### データモデル

`tasks` テーブルに `tsvector` の生成列（Generated Column）を持ち、title に `pg_trgm` の trigram index を張る。

PostgreSQL 標準の `tsvector`（`pg_catalog.simple`）は空白・記号でしか語を切らないため、日本語の部分一致は取れない。そこで採用エンジンは **`pg_trgm`（標準）** とする。PostgreSQL 同梱の contrib で、PG13 以降は trusted extension なので DB への `CREATE` 権限で導入できる。`pg_bigm` は `USE_PG_BIGM=true` で切り替える任意の経路（ILIKE + `gin_bigm_ops`。拡張は運用側で別途導入する）である。設計は [タスク類似検索](https://github.com/koyori-app/task/blob/main/apps/backend/docs/task-similarity-search.md) に書いている。

```sql
-- USE_PG_BIGM=true の環境では、この生成列の代わりに title と description の gin_bigm_ops を張る
ALTER TABLE tasks
    ADD COLUMN search_vector tsvector
    GENERATED ALWAYS AS (
        to_tsvector('pg_catalog.simple',
            coalesce(title, '') || ' ' || coalesce(description, ''))
    ) STORED;

CREATE INDEX idx_tasks_search_vector ON tasks USING GIN(search_vector);

-- 部分一致・表記ゆれ用（title のみ）
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_tasks_title_trgm ON tasks USING GIN (title gin_trgm_ops);
```

DB の `lc_ctype` が `C` だと `pg_trgm` は日本語の trigram を作らないため、マイグレーションは `show_trgm('日本語テスト')` が空なら止まる。

検索条件は次の OR（件数と一覧で同じ条件を使う）:

- `search_vector @@ plainto_tsquery('pg_catalog.simple', q)`（語の一致）
- `title` / `description` の `ILIKE '%q%'`（部分一致。日本語の中間一致・2 文字の語もここで拾う）
- `q <% title`（`word_similarity`。typo などの表記ゆれ）

対象は削除されていないタスクで、アーカイブ済みも含む。コメントの本文は検索しない。`USE_PG_BIGM=true` の経路は `title` / `description` の ILIKE だけで当て（`tsvector` と `word_similarity` は使わない）、更新日時の新しい順に返して `score` は常に 1.0 になる。

### API

```text
GET /tasks/search?q=OAuth&limit=20&offset=0
```

`q` は trim 後に空なら 400 である。`limit` は既定 20、上限 100（超過は丸める）で、プロジェクト内のタスクだけを探す。

レスポンス（title に一致する行を先に、次にスコア降順。同点は id 順）:

```json
{
  "tasks": [
    {
      "id": "uuid", "seq_id": 42,
      "title": "OAuth 対応を実装する",
      "highlight": "…<em>OAuth</em> Apps を使って…",
      "score": 0.92
    }
  ],
  "total": 5
}
```

`highlight` は title + description から検索語の最初の一致（大文字小文字を無視）を `<em>` で囲んだ抜粋である。前後の文字は HTML エスケープする。表記ゆれでのみ一致した行は `<em>` なしの先頭抜粋になる。`score` は `ts_rank` と `word_similarity` の大きい方で、ILIKE のみで一致した行は 0 になりうる。

説明文のメンションは `<@利用者ID>` の印で保存され、本文に名前は入らない。検索語の中の `@名` は、その名の者を印でメンションした説明文にも当たる（名前は検索のときに引くので改名に追従する）。範囲・同名の扱い・抜粋は [コメント・アクティビティ §3.2](/features/tasks/collaboration) の「検索」に書く。

### 類似タスク候補 API

タスク作成時の重複候補とタスク詳細の「似ているタスク」に使う。title 同士の trigram 類似度（`title % $title`、`pg_trgm.similarity_threshold` 既定 0.3）で候補を取る。

```text
GET /tasks/similar?title=ログイン画面&exclude_task_id=<uuid>&limit=5
```

| パラメータ | 必須 | 既定 | 制約 |
|---|---|---|---|
| `title` | ○ | | trim 後に空、または 255 文字（文字数）を超えたら 400 |
| `exclude_task_id` | | なし | 候補から除くタスク（詳細画面で自分自身を除く） |
| `limit` | | 5 | 上限 20（超過は 20 に丸める） |

レスポンス（`score` は `similarity(title, $title)` の降順。同点は id 順）:

```json
{ "tasks": [ { "id": "uuid", "seq_id": 42, "title": "ログイン画面の修正", "score": 0.58 } ] }
```

候補は **同一プロジェクト内** の削除されていないタスクに限る（同じテナントの他プロジェクトは出さない）。認可は `/tasks/search` と同じ（`read:task` とプロジェクトへのアクセス）である。

## 2. バルク操作

### API

```text
POST /tasks/bulk
```

リクエスト:

```json
{
  "task_ids": ["uuid1", "uuid2", "uuid3"],
  "update": {
    "status_id": "uuid",
    "assignee_id": "uuid",
    "add_label_ids": ["uuid"],
    "remove_label_ids": ["uuid"],
    "sprint_id": "uuid",
    "clear_sprint_id": false
  }
}
```

`update` のフィールドはどれも省略できる。

| フィールド | 動作 |
|------|---------|
| `status_id` | ステータスを変える。同じステータスなら何もしない |
| `assignee_id` | 担当者を 1 人追加する（役割は `assignee`。既に担当なら何もしない）。プロジェクトに入れない利用者はそのタスクの失敗になる |
| `add_label_ids` | ラベルを追加する（上書きではない）。プロジェクトに無いラベルはそのタスクの失敗になる |
| `remove_label_ids` | ラベルを外す。未付与・プロジェクト外の ID は無視する。`add_label_ids` と同じ ID を含むとリクエスト全体が 400 になる |
| `sprint_id` / `clear_sprint_id` | スプリントを設定する / 解除する。両方あれば解除を優先する |

`task_ids` は 1〜100 件で、重複は 1 件にまとめる。タスクごとに別のトランザクションで処理するので、1 件の失敗は他のタスクに影響しない。アクティビティはタスクごとに記録し、GitHub 連携のあるタスクは書き戻しを積む。

単体の更新 API と違って、次のことは行わない。

- `status_changed`・`assigned` の通知の送信とウォッチャーの追加
- 完了ステータスへ移すときの必須カスタムフィールドの確認
- 完了済みスプリントへの割り当ての拒否

**未実装**: 優先度・マイルストーンの変更、担当者の削除、アーカイブ、削除の一括操作。

レスポンス（`failed` の `reason` は `not-found` / `forbidden` / `conflict` / `bad-request` など）:

```json
{
  "updated": 2,
  "failed": [{ "task_id": "uuid3", "reason": "not-found" }]
}
```

### 一括作成

```text
POST /tasks/bulk-create
```

リクエスト（`tasks` の各要素は単体作成 `POST /tasks` と同じ形）:

```json
{
  "tasks": [
    { "title": "1 件目", "status_id": "uuid" },
    { "title": "2 件目", "status_id": "uuid", "assignees": [{ "user_id": "uuid", "role": "assignee" }] }
  ]
}
```

`tasks` は 1〜100 件。範囲外は 400 になる。認可（`write:task` スコープとプロジェクトへのアクセス）と検証は単体作成と同じ関数を通すので、担当者の確認・ラベル・カスタムフィールド・メンション通知・アクティビティ・Webhook も単体作成と同じ規則で働く。

- 全件を 1 つのトランザクションで処理する。**全件作られるか、1 件も作られないかのどちらか**で、一括更新と違い部分成功は無い
- 要素の失敗は 400 になり、メッセージは `tasks[i]: 理由` の形（`i` は 0 始まり。理由は `not-found` / `forbidden` / `conflict` / `bad-request` か、検証の詳細文）。直して丸ごと再送する
- 通知・アクティビティ・Webhook は件数分出る（`task.created` が 100 件なら 100 回届く）
- 同じリクエスト内のタスクは互いに参照できない。`parent_task_id` などは既存のタスクの ID だけを受け付ける。親子にするときは親を先に作り、次のリクエストで子を作る
- 採番のためにプロジェクトの採番行をロックするので、処理中は同じプロジェクトの他の作成が待たされる
- ロック順は単体作成と同じ「採番行 → スプリント」。要素のスプリントは UUID 昇順にまとめてロックするので、入力の並びにかかわらずスプリント完了処理（UUID 昇順）とデッドロックしない
- 再送の重複防止（冪等キー）は無い。応答が得られなかったときは一覧で確かめてから再送する

レスポンスは `201 Created` で、`tasks` に作成したタスクを入力と同じ順で返す（各要素は単体作成のレスポンスと同じ）。

## 3. 保存済みビュー

### データモデル

テーブルは `project_task_views` である。

```rust
pub struct Model {
    pub id: Uuid,
    pub project_id: Uuid,
    pub created_by: Uuid,
    pub name: String,
    pub is_shared: bool,
    pub filters: Json,
    pub sort: Json,
    pub view_type: String, // board | list | table
    pub created_at: DateTimeUtc,
    pub updated_at: DateTimeUtc,
}
```

| カラム | 型 | 制約 |
|--------|-----|------|
| `id` | UUID | PK |
| `project_id` | UUID | NOT NULL, FK→projects CASCADE |
| `created_by` | UUID | NOT NULL, FK→users CASCADE |
| `name` | VARCHAR(100) | NOT NULL |
| `is_shared` | BOOLEAN | NOT NULL DEFAULT false |
| `filters` | JSONB | NOT NULL DEFAULT '{}' |
| `sort` | JSONB | NOT NULL DEFAULT '{}' |
| `view_type` | VARCHAR | NOT NULL DEFAULT 'list' |
| `created_at` | TIMESTAMPTZ | NOT NULL DEFAULT now() |
| `updated_at` | TIMESTAMPTZ | NOT NULL DEFAULT now() |

サーバーは `filters` と `sort` の中身を検証せず、受け取った JSON をそのまま保存して返す。想定している `filters` の形は次のとおりである。

```json
{
  "status_ids": ["uuid"],
  "priority": ["high", "critical"],
  "assignee_ids": ["uuid"],
  "label_ids": ["uuid"],
  "sprint_id": "uuid",
  "milestone_id": "uuid",
  "deadline_before": "2026-07-01",
  "is_archived": false,
  "has_no_assignee": false
}
```

### マイグレーション

```sql
CREATE TABLE project_task_views (
    id UUID PRIMARY KEY,
    project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    created_by UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    name VARCHAR(100) NOT NULL,
    is_shared BOOLEAN NOT NULL DEFAULT false,
    filters JSONB NOT NULL DEFAULT '{}',
    sort JSONB NOT NULL DEFAULT '{}',
    view_type VARCHAR NOT NULL DEFAULT 'list',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_project_task_views_project ON project_task_views(project_id);
CREATE INDEX idx_project_task_views_project_created_by
    ON project_task_views(project_id, created_by);
```

### API

スコープは読み取りが `read:task`、書き込みが `write:task` である。

| メソッド | パス | 説明 |
|---------|------|------|
| `GET` | `/task-views` | 一覧（自分のビュー + 共有ビュー。名前順。`{ "views": [...] }`） |
| `POST` | `/task-views` | 作成。`view_type` は `board` / `list` / `table` のいずれか |
| `PATCH` | `/task-views/{view_id}` | 更新（作成者 or テナントオーナー） |
| `DELETE` | `/task-views/{view_id}` | 削除（作成者 or テナントオーナー） |

**未実装**: 保存済みビューの適用（`GET /tasks?view_id=uuid`）。`GET /tasks` は `view_id` を受け取らないので、ビューの `filters` を読んで一覧のクエリへ変換するのはクライアントの仕事である。

## 4. ファイル添付

Drive の `drive_files` をタスクへ紐付ける中間テーブル。

### データモデル

| カラム | 型 | 制約 |
|--------|-----|------|
| `id` | UUID | PK |
| `task_id` | UUID | NOT NULL, FK→tasks CASCADE |
| `drive_file_id` | UUID | NOT NULL, FK→drive_files CASCADE |
| `created_by` | UUID | NOT NULL, FK→users CASCADE |
| `created_at` | TIMESTAMPTZ | NOT NULL DEFAULT now() |
| `source` | VARCHAR(16) | NOT NULL DEFAULT `'manual'`。`manual`（手動添付）または `body`（Drive の Markdown 本文から抽出） |
| — | — | UNIQUE(task_id, drive_file_id) |

同じ `(task_id, drive_file_id)` は 1 行だけで、`source` はその行の由来を表す。`body` の行は Drive の Markdown ファイルを保存したときに自動で作られ、本文から参照が消えると自動で消える（[Drive 機能仕様 §8.5](/features/drive#85-本文からのタスク参照)）。結び付け先は手動添付と同じ範囲で、プロジェクトファイルから別プロジェクトのタスクへの参照はリンクにならない（別プロジェクトのタスクの添付一覧からファイル名が、元のプロジェクトに入れない人に見えてしまうため）。

### マイグレーション

```sql
CREATE TABLE task_attachments (
    id UUID PRIMARY KEY,
    task_id UUID NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    drive_file_id UUID NOT NULL REFERENCES drive_files(id) ON DELETE CASCADE,
    created_by UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (task_id, drive_file_id)
);
CREATE INDEX idx_task_attachments_task ON task_attachments(task_id);

-- m20261016010000_task_attachments_source
ALTER TABLE task_attachments ADD COLUMN IF NOT EXISTS source VARCHAR(16) NOT NULL DEFAULT 'manual';
```

### API

| メソッド | パス | 説明 |
|---------|------|------|
| `GET` | `/tasks/{id}/attachments` | 添付ファイル一覧（`{ "attachments": [...] }`。新しい順） |
| `POST` | `/tasks/{id}/attachments` | Drive ファイルを紐付け |
| `DELETE` | `/tasks/{id}/attachments/{attachment_id}` | 紐付け解除（Drive 本体は残る。添付の作成者 or テナントオーナー） |

`POST` リクエスト（先に Drive API でアップロードして `drive_file_id` を取得する）:

```json
{ "drive_file_id": "uuid" }
```

別のテナントのファイルと、別のプロジェクトに属するファイルは 403 である。レスポンスは `id` / `drive_file_id` / `name` / `mime_type` / `size` / `url`（コンテンツ URL）/ `created_at` / `source` を持つ。フロントエンドが MIME タイプを見て表示を出し分ける。

手動と自動（`source`）の優先規則は次のとおりである。

| 操作 | 既存の行 | 結果 |
|------|---------|------|
| `POST`（手動添付） | なし | `manual` で作成（`201`） |
| `POST` | `body` | `manual` に昇格（`200`）。解除できるのは昇格させた利用者とテナントオーナー |
| `POST` | `manual` | `409 Conflict` |
| 本文に参照あり | なし | `body` で作成 |
| 本文に参照あり | `manual` | そのまま（`body` に書き換えない） |
| 本文から参照が消えた | `body` | 削除 |
| 本文から参照が消えた | `manual` | そのまま |
| `DELETE` | `body` | `409 Conflict`。本文から抽出した参照は本文を編集して外す |
| `DELETE` | `manual` | `204` |

プレビューはサーバーで生成しない。API はコンテンツ URL と MIME タイプを返し、画面がブラウザで表示する（§6）。

**未実装**: サムネイルの生成。画像は `image` crate でのリサイズ、動画は `ffprobe` + `ffmpeg` によるバックグラウンドジョブでの抽出を想定している。動画サムネイルをまともに生成するには `ffprobe` / `ffmpeg` のサーバーへのインストールが必要である。

## 5. マイタスク API

テナントの中で、プロジェクトを横断して自分が担当のタスクを返す。アーカイブ済みと削除済みは除き、作成の新しい順に並べる。

```text
GET /v1/tenants/{tenant_id}/users/me/tasks?filter=today&limit=50
```

| パラメータ | 既定 | 内容 |
|---|---|---|
| `filter` | `all` | `all` / `today`（締切が今日）/ `week`（締切が今日から 7 日以内）/ `overdue`（未完了で Hard 締切を過ぎた）/ `no_due_date`（締切なし）。それ以外は 400。日付は UTC で判定する |
| `include_personal` | true | 個人プロジェクトのタスクを含めるか |
| `project_id` | なし | プロジェクトで絞る |
| `limit` / `offset` | 50 / 0 | `limit` の上限は 200 |

レスポンスは `{ "tasks": [...], "total": N }` で、各タスクは `seq_key`（`KEY-N`）と `project`・`status` の要約を持つ。スコープは `read:task` である。プロジェクトだけの客分には、明示メンバーのプロジェクトの分だけを返す。

`GET /v1/tenants/{tenant_id}/users/me/personal-project` は個人プロジェクトを返し、無ければ自動で作る。
