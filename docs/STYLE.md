`docs/` のページを書く・書き直すときの規則である。構成（どの群に何を置くか）、ページの形（frontmatter と節）、文章の規則、検査の順に書く。既存ページを新しい形へ移す作業は TASK-442 で進めており、移していないページは `scripts/lint-allowlist.txt` に載せてある。

## 読み手と群

読み手は 3 種類いる。使う人（利用者）、動かす人（セルフホストの運用者）、直す人（開発者）である。最上位の群は読み手で切り、1 ページは 1 種類の読み手に向けて書く。

| 群 | ディレクトリ | 読み手 | 書くこと | 文体 |
|---|---|---|---|---|
| はじめに | `getting-started/` | 全員 | Koyori の全体像、用語（ワークスペース・プロジェクト・タスク）、画面の歩き方 | 敬体 |
| 使い方 | `guide/` | 利用者 | 操作の手順。画面に出る文言で書く | 敬体 |
| セルフホスト | `self-hosting/` | 運用者 | 必要なもの、環境変数、外部サービスの登録手順、更新、セキュリティの前提 | 敬体 |
| 連携と API | `integrations/` | CLI・PAT・外部ツールを使う人 | アクセストークン、CLI、Webhook、API の入口、Desktop の認証 | 敬体 |
| 開発者向け | `dev/` | 開発者 | 仕様（`dev/features/`）、フロントエンド（`dev/frontend/`）、設計の記録（`dev/design/`）、開発手順（`dev/development/`） | 常体 |

各ディレクトリには `index.md` を置き、frontmatter の `sidebar.group.label` に日本語の群名、`sidebar.order` に並びを書く。`index.md` の本文は、その群に何があるかを 3〜5 行で案内する。

同じ事実は 1 か所にだけ書き、他の場所からはリンクする。定義元は次のとおりである。

| 事実 | 定義元 |
|---|---|
| 環境変数と設定手順 | セルフホスト |
| スコープ・CLI のコマンド・Webhook のペイロード | 連携と API |
| API の形、認可、データの列、現在の振る舞い | 開発者向け → 仕様 |
| 判断の理由と比較した案 | 開発者向け → 設計の記録、または仕様の「決定の記録」 |
| DB の列定義と SQL | `apps/backend/migration`（文書には転記せず、ファイルへのリンクを置く） |
| テストケースの一覧 | テストファイルの冒頭コメント（文書には書かない） |

URL は `/dev/features/...` のようにディレクトリをそのまま使う。旧 URL（`/features/...` など）からは `public/_redirects` で転送する。

## ページの形

### frontmatter

```yaml
---
title: スケジュール                      # 1〜6 語の名詞句。「〜仕様書」「〜設計書」「（フォローアップ）」は付けない
description: 期間に重なるタスク・スプリント・マイルストーンをテナント横断で返す API   # 1 文
status: implemented                      # 仕様（dev/features/）だけ。implemented / partial / planned / operational
updated: 2026-11-04                      # 本文を変えた日
sidebar:
  order: 11                              # 群の中の並び
---
```

`status` は仕様のページだけに付ける。使い方・セルフホストでは、無い機能は書かないことで伝える。 分割した仕様の親ページ（`features/<name>/index.md`）にも付ける。群の案内ページ（`features/tasks/index.md` など）には付けず、代わりに `sidebar.group.label` を書く。

### 仕様（`dev/features/`）の節

見出しは次の 9 つに限り、この順に並べる。無い節は省いてよいが、順は変えず、独自の節名を足さない。見出しに番号を付けず、節の区切りの `---` も置かない。雛形は `_template-spec.md` にある。

| 節 | 書くこと |
|---|---|
| 概要 | 何をする機能か、誰のためか、範囲外は何か。3〜5 文 |
| 用語 | このページで定義する語。3 語以上あるときだけ置く |
| 振る舞い | 利用者から見える規則。小節は 1 話題に 1 つ |
| データ | 列の表だけ。struct と SQL は書かず、列を追加した migration ファイルへの GitHub リンクを置く |
| API | エンドポイントの表と、表に書けない規則。JSON の例は形が `openapi.json` から読めないものだけ |
| 認可 | 「操作 / 誰が / スコープ」の表 |
| 画面 | URL、入口、操作、コンポーネントの表 |
| 未実装と既知の制限 | 未実装・差分・未決をここに集める。本文の他の節には書かない |
| 決定の記録 | 「日付 / 決定 / 理由」の表。追記だけを行う |

本文の節は現在の動作だけを現在形で書く。理由は 1 文まで添えてよい。採らなかった案、比較、起きうる事故の説明は「決定の記録」の理由の列に移す。

`status: planned` のページ（未実装の設計案）は、概要の先頭に「未実装の設計案である」と書いたうえで、節の形は仕様と同じにする。設計の本文を「未実装と既知の制限」へ押し込まず、実装したときに `status` と概要の 1 文を変えれば仕様になる形にしておく。

### 使い方・セルフホスト・連携の節

手順のページは「目的 → 前提 → 手順 → 確かめ方 → 困ったとき」の順にする。雛形は `_template-guide.md` にある。手順は番号付きの箇条書きで、1 項目に 1 操作を書く。画面の文言は「」で囲み、ボタンやメニューの名前は画面どおりに写す。

### 相互参照

`§5` や `3 節` のような番号参照は使わない。初見で何を指すか分からず、節を足すと番号がずれる。同じページの中は「[認可](#認可)の節」のように見出しの語で書き、別のページは「[スケジュールの認可](/dev/features/tasks/schedule#認可)」のようにページ名と見出しを並べたリンクにする。見出しの文言を変えるときは、参照している側も同じ PR で直す。

## 文章の規則

| 規則 | 理由 |
|---|---|
| 文体は群で決める（[読み手と群](#読み手と群)の表）。1 ページの中で混ぜない | |
| 1 段落に 1 話題。先頭の文で話題が分かるようにする | 1 つの箇条書きに場面が 3 つ入る文書が多かった |
| 1 文に因果は 1 つまで。「〜のは〜のため」の後に別の因果を続けない | 主語が途中で替わり、何の理由か追えなくなる |
| 括弧は 1 重まで。識別子の補足は文を分ける | |
| 表やコードの前は「次のとおりである。」のように文で終える。行末のコロンは書かない | lint の最多指摘だった |
| 太字は誤読を防ぐ否定に限り、1 つの節に 2 箇所まで。見出し代わりの太字は小節にする | |
| ダッシュ（em dash）を本文に書かない。表の中の `→` は列名で代える | |
| 比喩の名詞と造語を使わず、分野で通じる語に揃える（下の言い換え表） | 同じ概念に 2 つの名があると定義を探す手間が増える |
| 「利用者」に統一する。UI の文言と外部サービスの語の引用は除く | |
| 「未実装」は仕様の「未実装と既知の制限」の節にだけ書く | 同じ事実が 3 箇所に散っていた |
| 数字と単位、英数字と日本語の間は半角空白を入れる | |

言い換え表は次のとおりである。左の語は使わない。

<!-- lint-disable: term -->

| 使わない語 | 使う語 |
|---|---|
| 口 | エンドポイント |
| 旗 | フラグ |
| 控え、控える | 保存した値、保存する |
| 正本、正 | 定義元 |
| 防波堤 | 最後の制約 |
| 権威 | 判定の元 |
| 客分 | ゲスト |
| 札 | メンションのチップ |
| 印 | メンションのマーカー（`<@利用者ID>`） |
| 地雷 | 既知の落とし穴 |
| 沼 | （比喩をやめて、何が起きるかを書く） |

## 推敲と検査

- `pnpm lint:style`（`docs/` で実行）が[ページの形](#ページの形)と[文章の規則](#文章の規則)のうち機械的に見られるものを検査する。CI の `docs-lint` も同じスクリプトを回す
- 移していないページは `scripts/lint-allowlist.txt` に載せてあり、error が warn に落ちる。ページを書き直した PR でその行を消す
- ページを新しく書く・丸ごと書き直すときは、[yomiyasu](https://github.com/nanaism/yomiyasu) が使える環境なら仕上げに `/yomiyasu` を掛け、PR 本文に lint の件数の前後を添える。既存ページへの追記には掛けない。使えない環境では、この文書と `pnpm lint:style` だけで足りる
